# Security Policy

## Supported Versions

Only the latest release of PmGen receives security updates. Older versions are not supported and should be upgraded to the latest release as soon as possible.

| Version | Supported          |
|---------|--------------------|
| Latest  | :white_check_mark: |
| < Latest| :x:                |

## Security Architecture

PmGen uses a defense-in-depth approach with two independent signing/verification systems.

### ED25519 manifest signing

The auto-updater verifies every update before applying it:

1. The latest GitHub release contains three assets: `PmGen.zip`, `manifest.json`, and `manifest.json.sig`.
2. `manifest.json.sig` is a base64-encoded Ed25519 signature over the exact bytes of `manifest.json`.
3. The updater downloads both files, verifies the signature against the embedded public key (`SIGNING_PUBLIC_KEY_B64` in `pmgen/updater/updater.py`), and parses the manifest only after successful verification.
4. The manifest contains the SHA-256 hash of `PmGen.zip`. The downloaded ZIP must match this hash before extraction proceeds.
5. Extraction is guarded against path-traversal attacks.
6. Only cryptographically verified ZIPs are accepted for extraction and installation.

This ensures that an attacker who compromises the GitHub release page (but not the signing key) cannot inject malicious updates — the Ed25519 signature will fail verification.

### PFX code signing (Windows Authenticode)

A separate PFX certificate is used at build time to sign all EXE, DLL, and PYD files via `signtool.exe`. This is Windows Authenticode code signing with SHA-256 digest and DigiCert timestamping. It is applied by `build_sign_zip.py` during the release process.

The PFX certificate is **not** used for update verification. It provides Windows SmartScreen trust and anti-tampering for distributed binaries.

### Bootstrap deadlock considerations

If the Ed25519 private key is compromised, an attacker could sign malicious `manifest.json` files and publish updates that pass verification. Mitigations:

- **Key rotation**: Generate a new keypair with `generate_signing_keys.py`, update `SIGNING_PUBLIC_KEY_B64` in the source, and ship a new release. Compromised key is no longer trusted.
- **Recovery**: If the private key is compromised before key rotation is shipped, all users must manually upgrade to the key-rotated release. There is no remote key revocation mechanism.
- **Key separation**: The Ed25519 key pair and the PFX code-signing certificate are independent. Compromise of one does not affect the other.

## Key Management

| Key | Storage | Access | Rotation |
|-----|---------|--------|----------|
| Ed25519 private key | Environment variable (`PMGEN_SIGNING_KEY`) or key vault | Build machine only | Generate new keypair with `generate_signing_keys.py` |
| Ed25519 public key | Embedded in `pmgen/updater/updater.py` (committed to repo) | Read-only at runtime | Updated in source when private key rotates |
| PFX certificate | `helpers/IBSCert.pfx` (never committed) | Build machine, password-protected | Per certificate expiry |

**Rules**:

- Never commit private keys, PFX files, or signing passwords to the repository.
- The `PMGEN_SIGNING_KEY` environment variable must be set only in the build environment.
- PEM key files generated by `generate_signing_keys.py` (e.g., `signing_private.key`) must be stored outside the repository.
- The `.gitignore` should exclude `*.pfx`, `signing_private.key`, and `signing_public.key`.

## Dependencies

Runtime dependencies are pinned with exact versions in `requirements.txt`. PyInstaller build dependencies are managed separately.

- Keep all dependencies updated to the latest compatible versions.
- Review dependency changes for security advisories before updating.
- Run `pip-audit` or equivalent before releases.
- Third-party libraries with native code (e.g., cryptography, PyQt6) should be verified against their published signatures when possible.

## Disclosure Policy

1. Reporter submits vulnerability privately via email.
2. We acknowledge receipt within **72 hours**.
3. We investigate and provide an initial assessment within **5 business days**.
4. We develop and test a fix. The reporter is kept informed of progress.
5. We coordinate a release date with the reporter.
6. We publish the fix and a security advisory (if warranted) on the same day.
7. We credit the reporter in the advisory unless they request anonymity.

We follow a **90-day disclosure deadline**. If the vulnerability is not resolved within 90 days of the initial report, the reporter may choose to disclose publicly.
